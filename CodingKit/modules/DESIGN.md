# modules 通用代码设计理念

`modules/` 下的每个模块（`vofa+`、`ring_buffer`、`controller` …）都应当能被**不同工程、
不同 MCU、不同工具链**直接复用。为此约定以下设计理念。VOFA+ 模块是这套理念的参考实现。

一句话目标：**通用（可复用）、平台化（可移植）、解耦（可替换）、easy-to-use（好上手）。**

---

## 1. 解耦：核心 与 适配 分离

概念上分两类关注点，各层只依赖下层，绝不反向依赖：

| 关注点 | 职责 | 允许依赖 | 谁来写 |
|---|---|---|---|
| **核心** | 纯算法/协议逻辑 | 只有标准 C 库 | 模块作者，跨工程共用，**不用改** |
| **适配（移植 + 应用映射）** | 对接具体外设/驱动 + 业务数据映射 | 核心 + 平台驱动 + 业务结构体 | 使用者复制一份来改 |

判据：**核心层里不允许出现任何 `hal_*.h`、`fsp_*.h`、寄存器名、外设名。** 换 MCU 时核心
一个字节都不改，只改适配层。VOFA 里 `vofa.c/.h` 不含 UART/DMA/FSP，就是这条的体现。

> **文件别拆太碎。** “移植”和“应用映射”概念上是两件事，但落到工程里放进**同一个适配文件**
> （如 `vofa_cfg.c`：串口发送 + 接收 + 调参表）反而更好用——使用者只需复制、改一个文件。
> 文件多不等于解耦好；解耦看的是**依赖方向**，不是文件数量。VOFA 最终就是
> `vofa.c/.h`（核心）+ `vofa_cfg.c/.h`（适配）两对文件。

## 2. 依赖注入：能力用回调传入，不在核心里写死

平台能力（发送一帧、读一个字节、应用一条命令）以**函数指针**通过 `*_Init()` 注入核心，
而不是让核心去 `#include` 驱动。

```c
Vofa_Init(write_fn, command_fn, user);   /* 能力注入，核心与驱动零耦合 */
```

好处：核心可单元测试（注入假回调）、可换传输（UART/USB/EtherCAT 只换 write_fn）、
可多实例。

## 3. 平台化：一份源码，多种字长与工具链

- **字长抽象**：用 `CHAR_BIT` 判断，而不是假设 `char` 是 8 位。C2000/C28x 的 `char` 是
  16 位且没有真正的 8 位类型；核心用 `vofa_byte_t`（8 位 char 上是 `uint8_t`，16 位 char
  上是 `uint16_t`，低 8 位承载一个 octet）统一处理。**dead branch 不会送进缺 `uint8_t`
  的编译器**，两平台都能过。
- **显式字节序**：协议/存储一律显式序列化（位移取 octet），**绝不 `memcpy` 或直接发送
  浮点/整数的内存**，从而大小端 CPU 结果一致。
- **注释语言与编码**：注释用中文、写清楚关键实现（“好的代码 + 关键注释”，不是零注释）。
  真正的坑不是“用不用中文”，而是**编码不统一**：同一文件里混入 GBK/UTF-8/BOM 会让
  IAR、CCS(TI)、GCC 表现不一致甚至报错。约定：
  - **跟随工程既有约定**——本 RZ 工程是 **GBK / LF**，新文件也用 GBK/LF（用 `iconv`
    从 UTF-8 转，别用会破坏 GBK 字节的 UTF-8 编辑器直接改）。
  - **跨厂商模板层**（`modules/` 下待复用的原始文件）可保留 **ASCII 英文注释**，让不读
    中文的 C2000/其它工具链使用者也能直接用；落到具体工程后再本地化为中文。
  - 注释是给人看的，编译器会整行跳过，因此中文注释本身不影响 IAR/CCS/GCC 编译，
    前提是**单文件编码统一**。
- **标准库最小面**：优先用 C89/C99 保证可用的函数（如 `strtod` 而非可能缺失的 `strtof`），
  减少对特定 RTS 的依赖。

## 4. 静态分配，编译期可裁剪

- 不使用动态内存；所有缓冲区静态固定，大小由 `#ifndef` 宏在编译期确定。
- 每个可配置宏都有默认值 + `#error` 静态断言，误配置在编译期暴露。
- 用 `typedef char check[cond ? 1 : -1]` 之类的静态断言核对平台假设（如 float 必须是
  IEEE-754 binary32）。

## 5. 中断 / 主循环边界清晰

- ISR/DMA 回调**只做解析和入队**，绝不直接修改控制参数或调用重逻辑。
- 真正的“应用动作”只在主循环的 `*_Process()` 里发生。
- 跨上下文共享的数据用可覆盖的临界区宏保护：`VOFA_ENTER_CRITICAL()/EXIT_CRITICAL()`，
  默认空实现，工程按需覆盖（如 C28x 的 `DINT/EINT`）。

## 6. easy-to-use 是第一优先级

“安全、解耦”是底线，“好用”才是模块被复用的理由。具体要求：

- **上手三步以内**：实现一个回调 → `Init` → 调用一个发送/处理函数。
- **多档调用方式**：给数组版、可变参数版、以及自动数个数的宏版（`VOFA_SEND(...)`），
  让常见场景最省心，同时消除可变参数的类型陷阱。
- **一行增删配置**：业务映射用表驱动，加一个可调量 = 加一行（`VOFA_BIND(...)`），
  不改任何处理逻辑。
- **配置集中**：一个模块的所有可调项集中在头文件顶部或独立的表文件，不散落到入口函数。
- **命名一致**：`Module_Init / Module_Process / Module_SendXxx`，可预测。

## 7. 自带宿主测试

每个模块带可在 PC 上 `gcc` 直接跑的测试，覆盖编码/解析/边界/错误路径，不依赖硬件。
核心之所以能这样测，正是因为第 1、2 条的解耦与注入。

## 新模块检查清单

- [ ] 核心层不含任何平台头文件、寄存器、外设名
- [ ] 平台能力全部通过 `Init` 回调注入
- [ ] 用 `CHAR_BIT` 处理字长；协议/存储显式小端；源码 ASCII-only
- [ ] 无动态内存；可配置项有默认值和静态断言
- [ ] ISR 只入队，动作在 `*_Process()`；临界区宏可覆盖
- [ ] 提供数组 / 变参 / 宏三种调用方式，配置表一行可增删
- [ ] 附带 PC 宿主测试，`gcc -Wall -Wextra` 零告警
